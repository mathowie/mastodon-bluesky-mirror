# Optional Threads destination

Add Threads as a second destination for the same single-user Mastodon polling
worker. Public text, links, up to four images with alt text, and self-replies
are eligible from a separately persisted Threads activation time. Prepare
Threads text with a 500-character budget using the existing readable splitter.
Existing Bluesky mappings and exact saved post payloads remain authoritative.

Use Meta's documented Graph Threads API. Create unpublished media containers,
checkpoint their identifiers, check readiness, then publish. Image containers
reference the Mastodon attachment's public URL; no public NAS endpoint is
required. Keep the two destinations' failures, checkpoints and retries separate.

Implement additive `threads_sync_map` and `threads_sync_parts` SQLite tables.
Back up existing databases using the local SQLite backup API before adding
tables. Persist every part and publication intent before the remote write.
After a crash or uncertain publish response, inspect the saved container and
hold for review when the published post ID cannot be established. Never create
or publish another container as a guess. Definite failures use persisted bounded
retries with exponential backoff and server Retry-After; completed parts survive.

Threads remains disabled by default. Bootstrap a long-lived token using a
short-lived token and Threads app secret, or import a long-lived token with an
explicit expiry. Verify `/me`, pin the account ID, and atomically store renewable
credentials in a private file with mode 0600. Refresh before expiry; account
changes and invalid credentials fail closed. No secrets in responses, logs,
source payloads, or public repository fixtures. Setup can happen inside the
container, using the private environment file or hidden terminal prompts.

The dashboard selects a destination and shows its history, errors and retry
controls. Keep existing API defaults and Bluesky behavior compatible. Add
Threads connection status without disclosing credentials. Deployment requires
user-supplied Meta app authorization; build and test independently while that
setup is in progress. Only activate after verifying the destination identity.

The implementation uses existing Python, requests, FastAPI and SQLAlchemy
dependencies. Video, edit/deletion sync, native quote embeds, historical
backfill and grapheme-aware counting remain outside this addition.

API references: Meta's `fbsamples/threads_api` Postman collection and sample;
https://www.postman.com/meta/threads/collection/dht3nzz/threads-api .

Implementation choices: direct official API access avoids another hosted
service; separate destination tables minimize migration risk; uncertain writes
require review because Threads does not expose Bluesky-style client record keys.
